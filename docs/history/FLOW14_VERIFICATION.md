# FLOW-14 Verification and Strict Evidence Closure

## Release Status

> **FLOW-14: VERIFICATION COMPLETE — PENDING EXPLICIT USER APPROVAL**

FLOW-14 implements Reporting, Dashboards, Management Analytics, and Secure Exports as an additive, read-only observation boundary over authoritative AMMS state. It has **not** been marked APPROVED or FROZEN automatically. FLOW-01 through FLOW-13 remain approved/frozen. FLOW-10B physical DERMALOG SVT3000 SE integration remains explicitly deferred, and FLOW-15 has not started.

## Scope and Architecture

The reporting path remains:

> **Controller → FormRequest → Permission and AMMS organizational scope → read-only Query Service → allowlisted API Resource → Persian/Dari RTL UI**

The backend owns all business metrics. The React Reports Center presents server-defined metric cards, charts, registers, filters, and export lifecycle states; it does not recompute authoritative values in the browser. Date ranges are half-open and carry a declared timezone. Reporting queries use allowlisted filters and sorts, distinct Meeting identities, authoritative current Minute Versions, invalidation-aware official attendance, and applied historical event timestamps.[^metric][^scope]

## True MariaDB and Application Concurrency Evidence

The strict closure now includes controlled two-process races. Every worker uses a separate forked process, calls `DB::purge()` and `DB::reconnect()`, records PID and MariaDB connection ID, writes a ready marker, waits on a shared release barrier, records operation timing, and writes a result marker.

| Probe | Controlled orderings | Result |
|---|---|---:|
| ApplyMeetingCancellation versus Executive Dashboard | Dashboard entirely before cancellation; cancellation committed before dashboard | **PASS** |
| VerifyActionItemCompletion versus Action Item dashboard summary | Dashboard entirely before completion; completion committed before dashboard | **PASS** |
| Concurrent export generation | Two workers, one export UUID, same checksum/path, one authoritative artifact | **PASS** |
| Download versus expiry | Download wins before expiry; expiry commits before download | **PASS** |

Probe A records cancellation status and attendance invalidation in the same snapshot, preventing a hybrid view. Probe B records the before status counts, worker action, barrier, commit timing, and after status state; a completed item never appears without the corresponding pending count transition in one dashboard response. Probe D records policy result, application result, export status, storage existence, worker identity, and timing; after committed expiry the artifact is denied and never served.[^concurrency][^exportrace]

The export manager was hardened only for this evidence-integrity issue. A MariaDB atomic `PENDING → RUNNING` claim ensures that concurrent workers do not create duplicate artifacts or duplicate lifecycle audits; non-MySQL test behavior remains on the existing transaction path. The true race artifact records exactly one `REPORT_EXPORT_STARTED` audit and one `REPORT_EXPORT_COMPLETED` audit.
